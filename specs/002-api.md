## 1. Goal
A small, read-only HTTP API over the synthetic sales data from spec 001, so a future
frontend and analysts can:
- check that the service is up,
- see what data exists (date range, regions, products, categories),
- get exact sales totals, filtered by date, product, category and region, and grouped
  by date, product, category or region.

The API also reserves the path and shape of a future forecasting endpoint. Forecasting
itself is out of scope here.

## 2. Non-goals
- No forecasting, causal analysis or recommendations. Section 6 only describes a planned
  contract. Nothing in v1 returns a forecast (D10).
- No metrics beyond the four in section 4: no gross revenue, discount amounts or
  averages (D11).
- No sales channel grouping or filtering (D9).
- No writes. The API never creates, changes or deletes data files.
- No persistent database and no cache. DuckDB runs in memory and reads the Parquet
  files on every request (D7).
- No authentication, users or rate limits. The API is for local use only.
- No frontend, no Meta or other LLM APIs, no external services.
- The API never reads `expected_demand.parquet` and never returns the true model
  parameters in `metadata.json` (`parameters`, including `base_demand`). See section 3.8.
- No customer-level or promotion-level endpoints in v1.

## 3. Conventions

### 3.1 Paths and versions
- `GET /health` stays at the root, exactly as it is today.
- All data endpoints live under `/v1`. A breaking change gets a new prefix (`/v2`).
- FastAPI's generated docs stay at `/docs` and the schema at `/openapi.json`.

### 3.2 Where the data comes from (D1)
The data folder is the `--out` folder of the spec 001 generator. It is found like this,
on **every request** (no caching, D7):

1. Read the environment variable `DEALPILOT_DATA_DIR`. If it is unset or empty, use
   `data/raw`.
2. If that path is absolute, use it as is.
3. If it is relative, join it to the **project root**. The project root is found by
   starting at the folder that holds the `dealpilot` package and walking up until a
   folder contains `backend/pyproject.toml`. In this repository that is
   `D:\DealPilot AI`, so the default data folder is `D:\DealPilot AI\data\raw`.
4. If the path is relative and no project root is found (for example, the package was
   installed somewhere else), the data is unavailable (503 `data_unavailable`, see
   section 3.7). The message says to set `DEALPILOT_DATA_DIR` to an absolute path.

The server's current folder never matters. The generator's `--out` default
(`data/raw`) is relative to *its* current folder, so to create the default dataset, run
the generator from the project root:

```
cd "D:\DealPilot AI"
backend\.venv\Scripts\python.exe -m dealpilot.data.generate --out data/raw
```

`data/` is already in `.gitignore`.

**Required files.** The v1 dataset is these five files: `metadata.json`,
`regions.parquet`, `products.parquet`, `orders.parquet`, `order_lines.parquet`. Every
`/v1` endpoint first checks that **all five** exist, even the ones it doesn't read, so a
half-generated folder is reported the same way everywhere. Each endpoint then reads only
the files it needs. Files v1 never reads and never requires:
`expected_demand.parquet`, `customers.parquet`, `promotions.parquet`.

### 3.3 Value formats
| Kind | Format | Example |
|---|---|---|
| Date | String, `YYYY-MM-DD` | `"2025-01-31"` |
| Money (USD) | String: digits, a dot, exactly 2 digits. No currency sign, no thousands separator, no exponent. Matches `^[0-9]+\.[0-9]{2}$`. (D4) | `"2026466.37"`, `"0.00"` |
| Count | JSON integer | `7935` |
| ID | String, exactly as in the Parquet files | `"P001"`, `"R03"` |

Money is summed exactly by DuckDB as `DECIMAL` (`line_total` is `DECIMAL(12,2)`, its sum
is `DECIMAL(38,2)`) and turned into text by DuckDB. It is never converted to a float
on the way. Money values are never negative in this data.

### 3.4 Query parameters
- Repeat a parameter to give several values: `?region_id=R01&region_id=R02`.
  Comma-separated values are not supported.
- Several values of one parameter mean "any of these" (OR). Different parameters must
  all match (AND).
- Parameter names and values are case-sensitive.
- On `/v1` endpoints, a parameter the endpoint doesn't define is an error
  (`unknown_parameter`), not ignored (D3). `/health` keeps today's behavior and ignores
  extra parameters.

### 3.5 Error convention (D12, D13)
**Scope.** This convention covers every request whose path is `/v1` or starts with
`/v1/`, including unknown `/v1` routes such as `/v1/forecasts`. All other paths,
including `/health` and unknown routes like `/nope`, keep FastAPI's standard responses
unchanged, for example `405 {"detail": "Method Not Allowed"}` for `POST /health` (D13).

**Status codes** (for `/v1` paths)

| Status | Meaning |
|---|---|
| 200 | Success |
| 404 | No such route |
| 405 | The route exists but not for this method |
| 422 | A request value is wrong. Every input problem uses 422, never 400. |
| 500 | Unexpected server error |
| 503 | The data can't be read (folder or file missing, unreadable, wrong schema) |

**Body.** Every non-200 response from a `/v1` path uses this JSON body. FastAPI's
default `{"detail": ...}` body must never be returned for a `/v1` path.

```json
{
  "error": {
    "code": "invalid_date",
    "message": "start must be a date in YYYY-MM-DD format.",
    "details": [
      {"parameter": "start", "value": "2025-13-01", "reason": "month must be 1 to 12"}
    ]
  }
}
```
- `code`: one of the codes below. Clients can rely on it.
- `message`: a sentence for people. Wording can change. It never includes stack traces
  or absolute file system paths. (A 503 may name the configured `DEALPILOT_DATA_DIR`
  value and file names; see section 3.7.)
- `details`: a list, empty when there is nothing to add. One entry per bad value.
  `parameter` and `value` are strings, or null when they don't apply.

| Code | Status | When |
|---|---|---|
| `invalid_date` | 422 | A date isn't a real `YYYY-MM-DD` date |
| `invalid_date_range` | 422 | `start` is after `end` |
| `date_out_of_range` | 422 | A date is before the dataset `start` or after its `end`. Never clipped (D2). |
| `unsupported_dimension` | 422 | `group_by` has a value not in section 5.4's list (including `channel`) |
| `invalid_filter` | 422 | A filter value is empty or doesn't exist in the data |
| `invalid_parameter` | 422 | Any other bad value: unknown enum value, repeated `group_by` value, `interval` without `group_by=date` |
| `unknown_parameter` | 422 | A query parameter the `/v1` endpoint doesn't define |
| `result_too_large` | 422 | The answer would have more than 20,000 rows (D6) |
| `not_found` | 404 | No such route |
| `method_not_allowed` | 405 | Route exists, method doesn't |
| `data_unavailable` | 503 | Data folder or a needed file is missing, unreadable, or doesn't match spec 001's schema |
| `internal_error` | 500 | Anything unexpected |

**Check order.** If several things are wrong, one error is returned. Checks run in the
steps below, and within a step in the order listed. The first check that fails decides
the response, and `details` lists every bad value for that check.

1. `unknown_parameter`: a query parameter the endpoint doesn't define.
2. Checks that need no data:
   1. `invalid_date`: `start` or `end` isn't a real `YYYY-MM-DD` date.
   2. `unsupported_dimension`: a `group_by` value isn't in section 5.4's list.
   3. `invalid_parameter`: unknown `interval` value, repeated `group_by` value, or
      `interval` without `group_by=date`.
   4. `invalid_filter`: an empty filter value (for example `product_id=`).
3. `data_unavailable` (503): the checks in section 3.7.
4. Checks against the data, after missing `start` and `end` are filled in from
   `metadata.json`:
   1. `invalid_date_range`: `start` is after `end`.
   2. `date_out_of_range`: `start` or `end` is outside the dataset range.
   3. `invalid_filter`: a filter value that doesn't exist in the data.
5. `result_too_large` (section 3.6).

So a request with both `start` after `end` and `start` before the dataset gets
`invalid_date_range`, and with missing data `?product_id=` gets 422 `invalid_filter`
while `?product_id=P999` gets 503 `data_unavailable`.

### 3.6 Result size (D6)
- A response from `/v1/sales/metrics` has at most **20,000 rows**. There is no
  pagination in v1.
- Exactly 20,000 rows is allowed.
- If the answer would have more rows, the API returns 422 `result_too_large` with no
  rows and no totals. The message tells the client to use a coarser `interval`, fewer
  `group_by` values, a shorter date range or more filters. `details` has one entry:
  `{"parameter": "group_by", "value": "<group_by values joined with commas>", "reason":
  "more than 20000 rows"}`. The exact row count isn't reported, because counting past
  the limit isn't needed.
- With no `group_by` there are no rows, so the limit can't be hit.
- Because only groups with sales are returned (D5), the size is only known after
  grouping. The implementation fetches at most 20,001 rows and rejects if it gets
  20,001.
- Real sizes with seed 42 over the full range: day 1,090; week x product 7,149;
  month x product x region 8,212; day x region 5,450 (all allowed). Day x product 48,427
  and day x product x region 143,547 are rejected.

### 3.7 When data is unavailable (503)
Every `/v1` endpoint returns 503 `data_unavailable` when any of these is true:
- no project root was found for a relative data path (section 3.2, step 4),
- the data folder doesn't exist,
- one or more of the five required files (section 3.2) is missing,
- a file it reads can't be read, `metadata.json` isn't valid JSON or lacks a field listed
  in section 5.2, or a Parquet file lacks a column listed in section 4 or has it with a
  different type.

The response must tell a person how to fix it, without exposing absolute paths:
```json
{
  "error": {
    "code": "data_unavailable",
    "message": "Sales data is not available. From the project root, run `backend\\.venv\\Scripts\\python.exe -m dealpilot.data.generate --out data/raw`, or set DEALPILOT_DATA_DIR to a folder made by the generator.",
    "details": [
      {"parameter": "DEALPILOT_DATA_DIR", "value": "data/raw", "reason": "orders.parquet is missing"}
    ]
  }
}
```
- `details` has one entry per problem. `parameter` is `"DEALPILOT_DATA_DIR"`. `value`
  depends on the configured value:
  - unset or empty: `"data/raw"` (the default),
  - a relative path: that path exactly as written,
  - an absolute path: the placeholder `"<absolute path>"`. The path itself is never
    echoed, so no absolute path appears anywhere in the body.
- `reason` names the file and the problem (`orders.parquet is missing`,
  `products.parquet is unreadable`, `orders.parquet has no column order_date`, and so
  on), or says `data folder does not exist` or `project root not found`. It never
  contains a path other than a file name.
- `/health` never returns 503; it doesn't look at data.

### 3.8 Expected demand and true parameters stay out
Spec 001 section 6.3 and `docs/evaluation.md` section 4 say expected demand and the
generator's true parameters are never model inputs. The API serves observed sales only,
so it:
- never opens `expected_demand.parquet`,
- never returns `metadata.json` `parameters` (trend rates, seasonality, promo lift,
  `base_demand` and the rest), and
- never returns `regions.size_weight`, which is a true demand parameter.

## 4. Data the API uses
All from spec 001 section 4 (types as DuckDB reads them):

| Table | Columns used |
|---|---|
| `orders` | `order_id` (VARCHAR), `order_date` (DATE), `region_id` (VARCHAR) |
| `order_lines` | `order_id` (VARCHAR), `product_id` (VARCHAR), `quantity` (BIGINT), `line_total` (DECIMAL(12,2)) |
| `products` | `product_id`, `name`, `category` (VARCHAR), `launch_date` (DATE), `discontinue_date` (DATE, nullable) |
| `regions` | `region_id`, `name` (VARCHAR) |
| `metadata.json` | `seed`, `start`, `end`, `generator_version`, `row_counts`, `library_versions` (optional) |

Not used in v1, although they exist: `orders.customer_id`, `orders.channel` (D9),
`order_lines.line_no`, `unit_price`, `discount_pct`, `promo_id` (D11),
`products.list_price` (D8), `regions.size_weight` (section 3.8).

The four v1 metrics (D11), always over the order lines that pass the filters:

| Metric | Definition | JSON type |
|---|---|---|
| `units` | `SUM(order_lines.quantity)` | integer |
| `revenue` | `SUM(order_lines.line_total)`: after discounts, in USD | money string (3.3) |
| `orders` | `COUNT(DISTINCT order_id)` | integer |
| `order_lines` | `COUNT(*)` of order lines | integer |

Important: an order can hold several products. So **`orders` does not add up across
`product` or `category` groups**. With seed 42 in January 2025, the total is 2,354
orders, but the five category rows add up to 5,229. `orders` does add up across `date`
and `region` groups, because an order has one date and one region. `units`, `revenue`
and `order_lines` add up across every grouping.

## 5. Endpoints in v1

### 5.1 `GET /health` (exists, unchanged)
Liveness only: "the process is up". It never reads data, so it answers even when the data
folder is missing.

- Parameters: none. Extra parameters are ignored, as today (D3).
- 200 response, exactly as today:
  ```json
  {"status": "ok", "version": "0.1.0"}
  ```
  `version` is `dealpilot.__version__`.
- Errors: none of its own, and no custom error handling (D13). A wrong method gets
  FastAPI's standard response, unchanged: `POST /health` returns 405 with
  `{"detail": "Method Not Allowed"}` and the header `Allow: GET`.
- Tests: the existing `tests/test_api_health.py` stays as it is, plus AC-API-01.

### 5.2 `GET /v1/metadata`
What dataset is loaded.

- Parameters: none.
- Reads: `metadata.json` only.
- 200 response:
  ```json
  {
    "seed": 42,
    "start": "2023-01-01",
    "end": "2025-12-31",
    "generator_version": "0.1.0",
    "library_versions": {"python": "3.13.17", "numpy": "2.5.4", "pyarrow": "26.0.0"},
    "row_counts": {
      "regions": 5, "products": 50, "customers": 2000, "promotions": 40,
      "orders": 90643, "order_lines": 246500, "expected_demand": 274000
    }
  }
  ```
- Rules:
  - Values are copied from `metadata.json` unchanged.
  - `library_versions` is `null` if the file doesn't have it (files from before it
    existed).
  - `parameters` is never included (section 3.8). `row_counts` may include
    `expected_demand`, because a row count isn't a model input.
  - Any other field in `metadata.json` that isn't listed above is not returned.
- Errors: `unknown_parameter` (422). `data_unavailable` (503) in the cases of section
  3.7, including when `metadata.json` isn't valid JSON or lacks `seed`, `start`, `end`,
  `generator_version` or `row_counts`.

### 5.3 `GET /v1/dimensions`
What you can filter and group by.

- Parameters: none.
- Reads: `metadata.json` (`start`, `end`), `regions.parquet`, `products.parquet`.
- 200 response (lists shortened):
  ```json
  {
    "date_range": {"start": "2023-01-01", "end": "2025-12-31"},
    "group_by": ["date", "product", "category", "region"],
    "intervals": ["day", "week", "month"],
    "metrics": ["units", "revenue", "orders", "order_lines"],
    "regions": [
      {"region_id": "R01", "name": "North"},
      {"region_id": "R02", "name": "South"}
    ],
    "categories": ["Apparel", "Electronics", "Home", "Office", "Outdoor"],
    "products": [
      {"product_id": "P001", "name": "Nova Speaker", "category": "Electronics",
       "launch_date": "2023-01-01", "discontinue_date": null},
      {"product_id": "P018", "name": "Halo Lamp", "category": "Home",
       "launch_date": "2023-01-01", "discontinue_date": "2024-07-06"}
    ]
  }
  ```
- Rules:
  - Product fields are exactly `product_id`, `name`, `category`, `launch_date` and
    `discontinue_date`. Each is a column of `products.parquet`, but not every column of
    that file is exposed (D8, D14). `discontinue_date` is `null` for products still sold
    at the end. `list_price` also exists in the file but is left out in v1: it is only
    the price at `--start` (spec 001 section 4) and changes every January 1.
  - Region fields are `region_id` and `name`. `size_weight` is left out (section 3.8).
  - `regions` is sorted by `region_id`, `products` by `product_id`, and `categories`
    alphabetically. `categories` holds the distinct values of `products.category`.
  - `group_by`, `intervals` and `metrics` list exactly what `/v1/sales/metrics` accepts.
- Errors: `unknown_parameter` (422). `data_unavailable` (503).
- Edge cases: a product with no sales at all is still listed, because the list comes
  from `products.parquet`, not from sales.

### 5.4 `GET /v1/sales/metrics`
Exact sales totals for a date range, optionally filtered and grouped.

**Parameters**

| Name | Type | Default | Rules |
|---|---|---|---|
| `start` | date | dataset `start` | Real date; not before dataset `start` or after dataset `end` (D2); not after `end` |
| `end` | date | dataset `end` | Real date; not before dataset `start` or after dataset `end` (D2) |
| `group_by` | repeatable enum: `date`, `product`, `category`, `region` | none (totals only) | Each value at most once. Any combination is allowed. `channel` is not supported (D9). |
| `interval` | enum: `day`, `week`, `month` | `day` | Only allowed when `group_by` includes `date`; otherwise `invalid_parameter` |
| `product_id` | repeatable string | none (all) | Each value must be a `product_id` in `products.parquet` |
| `category` | repeatable string | none (all) | Each value must be a category in `products.parquet` |
| `region_id` | repeatable string | none (all) | Each value must be a `region_id` in `regions.parquet` |

**What is counted:** order lines whose order has `start <= order_date <= end` and that
match every given filter.

**Which rows are returned (D5):** only groups with **at least one counted order line**.
A group with no sales has no row. It is not returned as zero.

- This applies to dates too. A day, week or month with no counted sales has no row.
  That includes every closed day (December 25 and January 1, spec 001 section 5.7),
  and days before a filtered product's launch or after its discontinuation.
- A missing date bucket means zero sales in that bucket. A client that needs a complete
  series (for a chart, or for an average per day as in spec 001 section 8.1) must fill
  the missing buckets with zeros itself. The full list of buckets follows from `start`,
  `end` and `interval` using the rules below, so no extra data is needed.
- `totals` is unaffected: it always covers the whole range.

**Date buckets**
- `day`: one bucket per calendar day.
- `week`: weeks start on Monday (ISO). The row's `date` is that Monday, which can fall
  before `start`. Only days from `start` to `end` are counted, so the first and last
  weeks can be partial.
- `month`: the row's `date` is the first of the month, which can fall before `start`.
  Partial months are counted the same way.

**Group columns in a row:** `date` gives `"date"` (bucket start), `product` gives
`"product_id"`, `category` gives `"category"`, and `region` gives `"region_id"`. Rows are
sorted ascending by these columns in the order the client gave them in `group_by`: for
`group_by=region&group_by=date`, by `region_id` first, then by `date`.

**200 response**, with seed 42, `start=2025-01-01`, `end=2025-01-31`,
`group_by=category`:
```json
{
  "start": "2025-01-01",
  "end": "2025-01-31",
  "group_by": ["category"],
  "interval": null,
  "filters": {"product_id": [], "category": [], "region_id": []},
  "metrics": ["units", "revenue", "orders", "order_lines"],
  "rows": [
    {"category": "Apparel", "units": 1370, "revenue": "476362.53", "orders": 956, "order_lines": 1118},
    {"category": "Electronics", "units": 1963, "revenue": "201843.99", "orders": 1207, "order_lines": 1559},
    {"category": "Home", "units": 1453, "revenue": "305828.41", "orders": 963, "order_lines": 1170},
    {"category": "Office", "units": 1334, "revenue": "75557.51", "orders": 928, "order_lines": 1114},
    {"category": "Outdoor", "units": 1815, "revenue": "966873.93", "orders": 1175, "order_lines": 1495}
  ],
  "totals": {"units": 7935, "revenue": "2026466.37", "orders": 2354, "order_lines": 6456},
  "row_count": 5
}
```
- `start` and `end` are the values actually used, after defaults.
- `interval` is `null` unless `group_by` includes `date`.
- `group_by` is echoed in the order the client supplied it, which is also the order
  rows are sorted by (see "Group columns in a row" above). Without `group_by` it is `[]`.
- `filters` always has the keys `product_id`, `category` and `region_id`. Each holds
  that filter's values, de-duplicated and sorted ascending, or `[]` when the filter
  wasn't given.
- `totals` is computed directly over all counted lines, not by adding up rows, so
  `totals.orders` counts each order once.
- With no `group_by`, `rows` is `[]`, `row_count` is 0, and the answer is in `totals`.
- When nothing is counted, `rows` is `[]` and `totals` is
  `{"units": 0, "revenue": "0.00", "orders": 0, "order_lines": 0}`.

**Errors:** `invalid_date`, `invalid_date_range`, `date_out_of_range`,
`unsupported_dimension`, `invalid_filter`, `invalid_parameter`, `unknown_parameter`,
`result_too_large` (all 422); `data_unavailable` (503).

**Edge cases**

| Case | Result |
|---|---|
| `start == end` | One day. Valid. |
| Range is only a closed day (e.g. `start=end=2024-12-25`) | 200, `rows` `[]`, totals zero |
| `group_by=date` over a range with a closed day | That day has no row |
| `group_by=product` over a range before a product's launch | That product has no row |
| `category=Home&product_id=P001` (P001 is Electronics) | 200, nothing matches both, `rows` `[]`, totals zero |
| Same filter value given twice | Treated as once |
| `group_by=date` with no `interval` | Daily buckets |
| `interval=week` without `group_by=date` | 422 `invalid_parameter` |
| `group_by=date&group_by=date` | 422 `invalid_parameter` |
| `group_by=channel` | 422 `unsupported_dimension` (D9) |
| Empty value, e.g. `product_id=` | 422 `invalid_filter` |
| `start=2022-12-31` (before the data) | 422 `date_out_of_range`, never clipped (D2) |
| More than 20,000 groups | 422 `result_too_large` (D6) |

## 6. Forecasting: planned contract, not in v1 (D10)
**Status: planned. Not implemented. v1 returns no forecasts.** `/v1/forecasts` is not
registered in v1, so a request gets 404 `not_found` and the path is absent from
`/openapi.json`. Forecasting needs its own reviewed spec (003) before any code. This
section only reserves the path and shape so the frontend can plan around it. Spec 003
may change any of it.

Planned endpoint: `GET /v1/forecasts`

| Parameter | Type | Planned rule |
|---|---|---|
| `level` | enum: `total`, `category`, `product_region` | The levels in `docs/evaluation.md` section 3 |
| `category` | string | Required when `level=category` |
| `product_id`, `region_id` | string | Both required when `level=product_region` |
| `cutoff` | date | Last day of training data. Default: dataset `end`. |
| `horizon` | integer, 1 to 28 | Days forecast after `cutoff`. Default 28, the fold length in `docs/evaluation.md`. |

Planned response shape:
```json
{
  "level": "category",
  "key": {"category": "Outdoor"},
  "cutoff": "2025-12-31",
  "horizon": 28,
  "model": {"name": "seasonal_naive", "version": "0.1.0", "settings": {"lag_days": 7}},
  "uses_planned_promotions": false,
  "points": [
    {"date": "2026-01-01", "forecast": 0.0, "lower_80": null, "upper_80": null}
  ]
}
```

Rules any future version must follow (from `docs/evaluation.md`):
- Train only on observed sales on or before `cutoff`. Never read
  `expected_demand.parquet` or `metadata.json` `parameters`.
- Serve a model only if it beats seasonal naive on WAPE and MASE (section 2 there).
  Otherwise serve seasonal naive itself and name it in `model`.
- If planned promotions are used as future inputs, `uses_planned_promotions` is `true`.
- Interval bounds are `null` unless the model gives ranges.

## 7. Implementation notes (binding)
- Module layout: routes in `dealpilot.api`; SQL and data access in a new
  `dealpilot.analytics` module (AGENTS.md lists `analytics` as a domain).
- No SQL built from raw user input. Filter values are passed as DuckDB parameters.
  `group_by` and `interval` values map to fixed SQL fragments chosen from a fixed list.
- Money: sum as `DECIMAL` and cast to text in DuckDB, as
  `CAST(COALESCE(SUM(line_total), 0) AS DECIMAL(38,2))` then `VARCHAR`. The `COALESCE`
  matters: a sum over no rows is NULL, and the contract says `"0.00"`. Never pass money
  through Python `float`.
- Error scope (D13): FastAPI exception handlers are app-wide, so three handlers check
  the request path:
  - `HTTPException` (404, 405) and `RequestValidationError`: for `/v1` paths they build
    the section 3.5 body; for any other path they call FastAPI's own default handlers
    (`fastapi.exception_handlers`).
  - Any other exception (500): for `/v1` paths it returns `internal_error` in the
    section 3.5 body, with a generic message and no exception text; for any other path
    it returns what FastAPI returns by default, plain text `Internal Server Error` with
    status 500.

  So `/health` and other routes outside `/v1` respond exactly as plain FastAPI does, and
  `/health` itself gets no error code of its own.
- Weeks: DuckDB `date_trunc('week', order_date)` starts weeks on Monday, matching
  section 5.4. Months: `date_trunc('month', order_date)`.
- Read-only: never write to the data folder.
- No new dependencies: FastAPI, DuckDB and the existing lock are enough.
- DuckDB 2.0 relations have no `fetchone()`. Use `execute(...).fetchone()` or
  `fetchall()`.
